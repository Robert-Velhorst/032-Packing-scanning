# Android reference photos and resumable item drafts

Checkpoint: 2026-10-01. Android can select an existing reference photo or open an internal camera screen while preserving the item editor in encrypted temporary storage. Saving an item remains a separate, explicit action. Native camera/provider/lifecycle execution and Android image decoding still require device acceptance. iOS native reference photos are unavailable in this build.

## Traveller workflow

In **My items → Add item / Edit item**, choose **Choose reference photo** or **Take reference photo**. Incomplete fields, precision, the original unit system, care flags, packing-form drafts, scan edits and adopted geometry are preserved before opening the native screen. Selection does not enter an item into the library or change an existing record.

Protected workspaces retain normal background locking during permissions, camera and provider screens. On return, unlock the original workspace and use **Resume item photo draft**. A cancelled picker, declined camera permission or recoverable selection failure also retains the encrypted editor draft. Resume it, then save or cancel. The lock screen shows a generic notice rather than its item name, measurements or image. Guest selection can be resumed only in guest packs.

**Save item** stages a fresh local photo ID, commits the record and only then removes the old photo, replaced original scan and pending draft. **Cancel** leaves the previous item, photo and source intact. A resumed edit refuses to overwrite a saved item whose complete record has changed or disappeared since selection. A suggested item requires returning to the pack that started it. Changing display units while the draft is pending does not reinterpret its numeric fields.

Only one pending photo draft is permitted. Save, cancel or discard it before selecting another photo. **Discard item photo draft** is available even while locked and removes only the temporary draft/image. Pending drafts expire after ten monotonic minutes from preparation; completing, resuming and reading do not renew that deadline. They are not a durable draft history. Process restart, web reload, cache removal or low memory can end recovery. Saved packing records remain unchanged. A web reload loses the ticket; wait for expiry if it is no longer available to discard.

A reference photo does not establish dimensions, weight, surface completeness or physical fit. Photos are included in explicitly exported ordinary JSON backups; those files are unencrypted. Optional account backups do not automatically upload reference photos.

## Authority and privacy

`PackingPhotoPlugin` requires a live native capture-storage lease before preparing a draft and derives workspace/account identity from that authority. JavaScript cannot select another scope or supply a URI, path, camera destination or remote image URL. The retained native plugin call drops its plaintext draft argument after borrowing it. One selection is active at a time; read/discard work has a four-job bound and rejects overload rather than leaving selection permanently busy.

Existing-photo selection uses the Android [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files), `ACTION_OPEN_DOCUMENT`, `CATEGORY_OPENABLE` and `image/*`. Only the returned `content:` URI is read. No broad storage permission, persistent URI grant, public copy or URI exposure to JavaScript is added. The chosen provider can itself be remote; the app does not configure or automatically upload to that provider.

The non-exported `ReferencePhotoActivity` uses Camera2. JPEG bytes remain in memory until the encrypted store accepts them; there is no camera-output file in the gallery or a plaintext temporary image file. `FLAG_SECURE` is requested for this camera activity. Back/cancel returns to draft recovery. Camera/session/ImageReader/surface resources close on pause/destroy, stale camera callbacks are refused, and shutter/expiry timeouts prevent an indefinitely pending capture. Camera output prefers the largest supported JPEG with a longest edge at most 2048 pixels; its bounded fallback is at most 4096 pixels and 16 megapixels.

Preview transforms undo TextureView stretching, fit the buffer uniformly and compensate display rotation, including display-change notifications. JPEG orientation is recorded separately. These follow Android's [camera preview](https://developer.android.com/media/camera/camera2/camera-preview) and [resizable preview guidance](https://developer.android.com/codelabs/android-camera2-preview); hardware orientation, framing, focus and front-camera behavior remain unverified.

`PendingItemPhotoStore` uses a dedicated `packing-photo-pending` cache directory and purpose-bound AES-256-GCM staging through `PendingBackupStore`. A fresh random key and nonce protect each stage. Authenticated data binds the ticket, workspace, account and storage purpose; the authenticated plaintext is a versioned `PIP1` draft/photo bundle. Original requests bind their completed receipt, preventing a camera result from substituting another ticket. No plaintext draft remains in the native ticket registry. Completion transfers the original scope and original expiry deadline.

Accepted source signatures are JPEG, PNG, GIF and WebP, with an enforced **12 MiB** input limit independent of provider metadata. SVG and unsupported formats are refused. The editor draft has a separate bound of 80 MiB minus 12 MiB and its eight-byte header; only one pending draft exists, with two encrypted stages allowed transiently during completion. Repeated selection, malformed payloads, altered ciphertext and cross-workspace/account reads fail closed.

Read requires a fresh live lease for the same workspace/account, checked before and after decryption/decoding. `ReferencePhotoDecoder` checks image bounds before pixel allocation, rejects more than 100 megapixels, samples to a longest edge at most 2048 and applies supported EXIF orientation. Rendering to a new JPEG removes source EXIF/GPS/camera metadata; animated input becomes a single reference image. JavaScript receives a bounded local JPEG and editor draft only after those checks. The Android decoder has compiled acceptance tests but has not been executed on a device here.

The process-owned runtime preserves pending selections across main-activity recreation and checks expiry every minute, independently of plugin teardown. Expired staging keys are dropped and owned encrypted files removed. Startup cleans only flat owned UUID `.sealed` / `.partial` files and preserves unknown files/directories. Native staging keys are independent of workspace data keys and deliberately survive a workspace lock solely for this limited, authenticated recovery. Raw owned buffers/keys are wiped where possible; strings, platform bitmap/compression/crypto copies and garbage collection cannot be guaranteed erased. Failed deletion can leave keyless ciphertext until startup cleanup.

## Storage boundaries and remaining acceptance

Record/photo/source writes are separate operations across IndexedDB and native storage. On a pre-commit failure, newly staged photos are removed when their session remains available; a lock may leave an unreferenced encrypted photo. Post-commit cleanup failure reports a saved item with incomplete cleanup, rather than reporting a failed save. Discarding or expiring a photo draft while locked cannot delete a newly captured, unsaved 3D source without reopening its scope; that source may remain until that workspace's original-capture cleanup. No scan IDs or private fields are exposed to the locked discard path.

Local proof: 265 web/server tests, client/server type checks and production build pass. Android has 79 passing unit tests, including eight encrypted photo-draft tests and four camera policy/preview tests. Debug assembly, lint and the instrumentation APK compile pass; APK signature/alignment/assets are recorded in [Android build verification](QA-ANDROID-BUILD.md). Lint and JavaScript bundle-size warnings remain disclosed there.

Chrome/Playwright at 1440×1000 and 375×812 uses actual Java encrypted staging/capture stores, real Web Crypto/IndexedDB and the real local account API with synthetic data. The simulated Capacitor boundary verifies partial cancellation, opaque encrypted staging, locking, stale/wrong-scope refusal, resume with original units after changing Settings, changed-record overwrite refusal, explicit save with a real displayed JPEG, and editing/removing a scan then cancelling without changing the original record/photo/source. Backup and browser workspace regressions pass both sizes. The synthetic JPEG is prepared with JVM ImageIO: this does **not** execute Camera2, the Android bitmap/EXIF decoder, OS permissions or document-provider callbacks.

A blocked provider read can delay worker cleanup and the callback despite the usable draft deadline. Provider timeout/low-memory behavior remains part of device acceptance.

Two compiled Android instrumentation cases cover bounded PNG→JPEG output and EXIF orientation/GPS/camera metadata removal; they were not run. Device acceptance must exercise those cases plus camera permission refusal/revocation, library providers, corrupt or enormous inputs, all orientation/fold/window changes, preview/shutter consistency, focus/exposure, concurrency with another camera app, background/rotation/activity recreation, process death, expiry, slow/broken providers, heap limits, lock ordering and actual WebView delivery. There is no phone/emulator, camera or personal-image execution evidence for this checkpoint. iOS parity, full scan/packing validation and the broader product goal remain unfinished.
