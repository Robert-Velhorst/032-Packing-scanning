# Android packing backup files

Checkpoint: 2026-10-01. This implements native Android saving and selection of ordinary packing JSON backups. iOS native backup files are unavailable in this build. Actual Android document-provider callbacks and lifecycle behavior still require a physical-device run; local proof uses the production storage core with a simulated Capacitor boundary.

## What the traveller does

In Android **Settings → Save backup file**, choose a destination in the system document picker. The app reports saved only after the selected provider's output stream closes successfully. Cancelling reports cancellation. A failed write warns that the selected destination may contain an incomplete file and asks for a new destination. Neither cancellation nor a save failure changes the packing workspace.

The exported file is **unencrypted JSON**, including packing records and locally saved reference photos. The system picker can offer cloud providers: selecting one deliberately copies the backup there. No automatic upload or account connection is involved. Original scan files are excluded; explicitly adopted packing shapes and bag cavities remain in the records. The original source links are removed when restoring.

In **Settings → Choose backup file**, choose a document. Selection alone does not restore anything. Protected workspaces remain subject to their normal background lock while the provider is open. The lock screen retains a generic pending-selection notice without showing backup contents. Unlock the same workspace, then open **Settings → Review selected backup**. For a selection made in guest packs, return to guest packs. The native core checks both workspace and account identity; choosing another workspace never redirects a pending restore into it.

Review validates the full backup and then asks to replace records and photos. The warning explicitly states that existing original scan files in the selected workspace are also removed, because the JSON backup cannot restore them. Guest packs and other workspaces remain. Cancelling this confirmation retains the selection for another review; **Discard selected backup** removes it without changing packing records. An invalid or unsupported backup fails before confirmation or record changes.

After confirmed restore, image IDs are remapped to staged local records, the selected workspace's records are committed, unreferenced photos and that scope's original captures are removed, and the temporary selection is discarded. These are separate storage systems: if post-commit cleanup fails, the restored records remain committed and the app reports the limitation. A background lock or workspace switch prevents stale review callbacks from beginning replacement. Previously staged photos are cleaned on a pre-commit failure where their storage session remains available.

## Native authority and temporary storage

`PackingFilesPlugin` uses Android's [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files): `ACTION_CREATE_DOCUMENT` and `ACTION_OPEN_DOCUMENT` with `CATEGORY_OPENABLE`. Only the `content:` URI returned by the system callback is used. JavaScript cannot supply a URI, local path, remote URL, destination filename, or another workspace identity. No persistent URI grant is requested or URI returned to JavaScript. No broad storage permission is added. Generic document MIME types are allowed for providers that label JSON as text or binary; actual content is validated independently.

The caller must supply a live capture-workspace lease before requesting either dialog. The plugin captures public workspace/account identity from the current native authority. The import result exposes only a random ticket and its target workspace label/ID; the JSON is returned only by a separate read with a newly live lease for that same identity. Native checks run before and after decrypting. The web root retains results across the protected packing view's unmount and refuses a late review result after locking or changing selection. There is one active document operation and at most four queued read/discard jobs.

`PendingBackupStore` streams incoming bytes into an encrypted file under app-private **cache**, with no plaintext temporary file. Each selection has a fresh 256-bit key and nonce; AES-GCM authenticates the entire file before bytes reach UTF-8/JSON parsing. The `PBK1` envelope contains a 12-byte nonce and a 128-bit tag. Associated data binds the version, random ticket, workspace, account and the dedicated storage purpose. Guest selection uses a separate identity. The full UTF-8 byte limit is **80 MiB**, independent of provider size metadata; empty, oversized, damaged and truncated files are refused. UTF-8 decoding rejects malformed bytes.

At most two encrypted selections can exist, allowing a pending import and an explicitly requested export snapshot. Their independent keys stay only in native process memory; they are **not** the workspace data key and are not persisted in Keystore, files, preferences, or backup metadata. Keeping a selected document through a workspace lock intentionally retains this limited staging authority, while reading it still requires unlocking its original workspace. Owned byte buffers and raw staging keys are zeroed on release; Java/JavaScript strings, cryptographic-provider copies and memory reclamation cannot be guaranteed erased.

Selections expire after ten monotonic minutes, without renewal by reads. Periodic cleanup drops their keys and removes their encrypted files. Process restart makes old selections unrecoverable; plugin load cleans only flat owned UUID `.sealed`/`.partial` files. Unknown files/directories are preserved and canonical boundaries reject paths outside the dedicated cache directory. Filesystem deletion failure can leave an encrypted, keyless orphan until a later startup cleanup. A web reload loses the pending ticket; choose the file again after discarding any known selection or its expiry. Cache deletion, process death and low memory can end a pending operation without altering existing packing records.

Explicit export is prepared while the original workspace lease is live. Its encrypted snapshot can be written to the specifically selected provider after the picker locks the workspace; this does not permit reading current workspace records while locked. The payload is removed from retained plugin-call arguments once borrowed. Failed or cancelled exports discard the staging key and file. No changes were made to optional account-export limits or provider settings.

## Verification and device acceptance

Eight production-core Android/JVM tests cover encryption, same-workspace/account reads after re-selection, guest/cross-workspace refusal, limits, empty/throwing/short/zero-read streams, strict UTF-8, altered ciphertext, cross-ticket copying, expiry, bounds on pending selections, discard, process restart, unknown-file preservation, traversal and closure. The complete Android suite has 79 passing tests; web/server tests have 265 passes. Client/server type checks, production build, debug assembly, lint, APK signature, 16 KiB alignment and all packaged web-asset comparisons pass. Lint retains 25 warnings; the JavaScript bundle retains its size warning.

Installed Chrome/Playwright at 1440×1000 and 375×812 runs real Web Crypto/IndexedDB, the production Java temporary/capture storage cores, and native account transport against the real local account API with synthetic data. The simulated native boundary covers export cancellation/success/failure, picker cancellation, encrypted opaque selection through locking, stale/wrong-workspace refusal, cancelled then confirmed replacement, real protected record/photo restore, scoped original-capture removal, guest preservation, invalid JSON and discard. The native flow has no console/page errors or warnings. The existing browser workspace regression also passes both sizes; its four `ERR_INTERNET_DISCONNECTED` account-session errors are expected from deliberately offline scenarios, with no unexpected errors or warnings.

Physical Android acceptance remains required: actual WebView/native round trips, file-provider names and permissions, chooser cancellation/back navigation, external-cloud-provider handling, callback/lifecycle ordering, process death during reads/writes, cache/low-memory limits, slow or broken providers, provider stream closure, idle expiry, background locking and partial-write recovery. No camera or physical packing accuracy was validated here. The bridge materializes up to an 80 MiB JSON string during review/export; Android heap/provider behavior at that maximum remains unmeasured. iOS native document flows and protected capture/workspace parity remain unfinished. This checkpoint does not complete product acceptance.

Build and raw evidence locations are recorded in [Android build verification](QA-ANDROID-BUILD.md). Previous artifacts and raw evidence are retained. No personal records, external provider configuration, deployment, publishing or commits were performed.
