# Android protected capture storage

Checkpoint: 2026-10-01. Android protected workspaces now connect encrypted packing records/photos to encrypted original captures through the unlock screen, scoped bridge and capture activity. The account service is still optional and unconfigured in the supplied debug build. Existing guest data remains separate and unencrypted. This connection has passed local core and simulated native-boundary checks; physical Android and iOS acceptance remain unfinished.

## Implemented storage boundary

`CaptureScopeManager` starts locked and holds only one selected scope. Deliberate guest selection or workspace opening requires the current selection revision. Every selection issues a new lease; old selections cannot reopen or lock a newer selection. A `CaptureStore` constructed with an `Access` retains that particular scope, rather than consulting a mutable current workspace when queued work eventually runs.

Protected access requires canonical workspace/account UUIDs and a 32-byte data key. The manager owns a copy, allowing the caller to erase its borrowed bytes after the handoff. Locking, replacing the scope or detecting five minutes of inactivity erases the manager's owned key buffer and revokes old access. Only explicit interaction through `touch()` renews the idle window; storage traffic does not. The web workspace, native activity lifecycle and capture-screen timer close access on locking, backgrounding, teardown or idle expiry.

The existing guest directory remains `filesDir/packing-scans`. Protected captures use `filesDir/packing-scans-protected/<workspace UUID>/<capture UUID>`. Guest files are neither migrated nor encrypted automatically. A protected store can delete or clear only its own root. Unknown non-capture files/directories are preserved. Canonical path checks reject traversal and relocated roots; callers cannot supply a file URL or public export path.

Original points and capture metadata are stored as `points.ply.sealed` and `capture.json.sealed`. Each file contains a four-byte `PSC1` format header, a random 12-byte nonce and AES-256-GCM ciphertext with a 128-bit authentication tag. Authenticated context binds the format version, workspace, account, capture UUID and logical filename. Moving ciphertext to a different identity or using the wrong key fails authentication. Protected reads have no plaintext-file fallback.

Serialization uses bounded in-memory buffers. Protected writes create encrypted partial files, synchronize their contents and rename them inside the selected capture folder; they never create a plaintext capture file. Failure or scope expiry rolls back the newly allocated capture folder. Process termination or a filesystem cleanup failure can leave an encrypted incomplete capture, which cannot be opened as valid geometry; no broader deletion is attempted. Renames of the two files are separate, rather than one directory transaction.

Reads bound metadata to 20,000 plaintext bytes and points to 8,000,000, with only the format overhead allowed on disk. The entire GCM tag is checked with `Cipher.doFinal` before any decrypted data reaches geometry parsing. This follows [Android's authenticated-cipher contract](https://developer.android.com/reference/javax/crypto/Cipher). The existing source validator still checks UUID, target, format, point counts, finite values, envelope and recorded dimensions. Preview, occupied reconstruction and cavity reconstruction retain their existing provenance hash of the original plaintext PLY. Reads do not rewrite original files.

## Bag draft save and source cleanup

The bag editor waits for a durable packing-record save before removing a superseded original source. Replacing the reusable bag record and linking a new bag to its pack use one saved app-state transaction. A save failure keeps the editor open for retry or cancellation, preserving the previous saved bag and its original capture. Packed positions and the other saved records are retained; a geometry change can still pause a conflicting plan.

Save, capture and draft-source cleanup have exclusive operation guards. Editing, Save, Cancel, header close and backdrop dismissal cannot race a pending operation. A failed cleanup while rescanning keeps every new draft source tracked in that mounted editor. Saving retains the selected source and attempts obsolete-source removal after the durable save; cancelling retries removal of draft sources only. Cancellation stays open if removal cannot be confirmed and never removes the original saved bag source.

A workspace lock or switch revokes the pending operation's storage and capture authority. It cannot publish a stale save or fall back to guest cleanup. If the workspace closes while a draft is pending, the in-memory editor and draft-source tracking do not survive. Already completed but uncommitted native captures can remain encrypted in their original protected workspace. Configured [raw-source retention](RAW-SCAN-RETENTION.md) can remove eligible point data later; confirmed local-data/workspace removal also covers that workspace's sources. There is no per-orphan recovery browser or cross-store cleanup service. A successful record save with failed subsequent cleanup is disclosed as saved with incomplete original-source removal, rather than reported as a failed save or silently rolled back.

The 2026-10-01 failure checks abort a real encrypted IndexedDB transaction, delay actual encryption/capture output, simulate a source-deletion failure and revoke workspace authority through the synthetic native boundary. They prove the local software ordering and retry behavior, including packed-lock preservation. Actual phone lifecycle, process loss and storage hardware failures remain unverified. See [dated build evidence](QA-ANDROID-BUILD.md).

## Connected workflow

On a configured Android installation, create a protected account workspace in Settings or choose an existing workspace and unlock it offline. Creation defaults to an empty workspace. An explicit guest copy preserves its originals and excludes original scan links. Newly captured originals belong to the selected protected workspace.

Creation/unlocking borrows the existing workspace data key only during the native handoff, then erases the borrowed byte array. Active browser keys remain non-extractable. The native call removes its key field and erases its owned input buffer; diagnostic logging is disabled. A device passphrase change rewraps the same data key, preserving encrypted original bytes.

Each mounted packing interface retains an immutable capture client and lease. Native calls validate it before queueing and again before returning private results. The capture activity uses the same authority and store. Replaced/closed clients refuse late replies; native stale work cannot read or remove another workspace's files. Native storage failure or an invalid handshake keeps the interface locked; it cannot silently fall back to guest records. Explicit retry can recover the connection.

Locking, account changes, sign-out and forgetting device sign-in close the web and native workspace. Android pause/stop callbacks revoke protected capture authority. Only the explicit transition to a live, foreground, same-lease capture activity preserves it; leaving that activity locks it too. This follows [Android's activity transition ordering](https://developer.android.com/guide/components/activities/activity-lifecycle), but actual camera permissions, ARCore installation, rotation and background/resume still need phone acceptance. Permission/install dialogs may require unlocking and retrying after the dialog.

Confirmed restore and local clearing remove original scans only from the currently selected scope. Workspace removal verifies the current passphrase/revision before clearing its original captures and removing its local registration. Native files and IndexedDB cannot share one transaction; failed cleanup/removal explicitly warns about potentially removed files and unconfirmed record removal. Guest and other workspace stores remain separate.

iOS protected workspaces stay disabled pending its own encrypted capture implementation and Mac/device verification. Browser protected workspaces retain their existing path. This Android connection does not claim complete platform or physical packing acceptance.

## Privacy limits and acceptance

Directory/capture identifiers, file sizes, existence and filesystem timestamps remain visible. Guest data and deliberate ordinary exports remain unencrypted. While a scope is open, its decrypted points, metadata and reconstruction results exist in memory. Explicit buffer erasure is best effort: Java cryptographic providers, strings, geometry objects and runtime copies are not guaranteed to be wiped. This does not protect against malicious app scripts, screenshots, an unlocked compromised device or someone who knows the device passphrase.

Local JVM checks execute the production scope manager, encrypted filesystem store and geometry algorithms using synthetic depth points. They cover item/interior reconstruction, source preservation, nonce separation, authentication failures, cross-identity copies, wrong keys, scoped cleanup, guest preservation, closed/stale operations, queued work after switching, key ownership/erasure, idle expiry and rollback between the point and metadata writes. These are not camera, Android cryptographic-provider, operating-system lifecycle or physical packing acceptance checks.

The complete Android suite now passes 67 tests, including 13 protected-store and three runtime/foreground authority checks, with no failures, errors or skips. Web/server tests now pass 260 checks across 34 files, and production type checks/build pass. Debug assembly and lint pass with zero errors and 21 warnings. The separately preserved debug APK passes v2 signature and 16 KiB ZIP-alignment checks; all seven final web assets match dist. See [dated build evidence](QA-ANDROID-BUILD.md).

Chrome at 1440×1000 and 375×812 runs actual Web Crypto/IndexedDB against the production Java scope/store/geometry code and real account transport/API over isolated TLS through a simulated Capacitor boundary. Creation/copy, scan/save/preview/reconstruction, locked lease refusal, offline key handoff, simulated background lock, guest/account isolation, account-mismatch locking, passphrase rotation without rewriting originals and scoped removal pass. A separate phone-sized test refuses failed/malformed storage and recovers through explicit retry. The existing complete browser workspace regression also passes at both sizes. No physical camera, Android cryptographic provider, native activity callback or system file dialog is exercised by these browser checks.

The account service stays optional and disabled in the supplied build. No personal records, provider deployment, automatic upload or public capture export is introduced by this core.

Android ordinary JSON backup files now use system document dialogs and encrypted, expiring selections with same-workspace review after unlocking. They exclude original captures, and confirmed replacement explicitly removes the selected workspace's previous originals. Actual OS document-provider and lifecycle execution remain unverified. See [native backup workflow and evidence](NATIVE-BACKUP-FILES.md).
